# Partner API keys, contributor tokens and abuse

A partner app's API key identifies the app and lets it submit for its contributors under pseudonymous IDs it chooses ([ADR 0011](0011-no-anonymous-edits-pseudonymous-partner-ids.md)). A key built into a mobile app can be pulled out of the app and used to send submissions under invented pseudonymous IDs, each of which looks like a new contributor with a clean trust score. RFC 8252, the OAuth best current practice for native apps, says it directly: "Secrets that are statically included as part of an app distributed to multiple users should not be treated as confidential secrets, as one user may inspect their copy and learn the shared secret" (section 8.5, [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.txt)).

## Decision

**API keys are server-side secrets.** Every key is held by a partner app's server and never shipped in a mobile app, desktop app or web page. A key has scopes: `read`, `submit` (submissions sent by the partner's server) and `mint_tokens`. The terms of service make shipping a key in a client a breach, and a key found in one is revoked as compromised.

**Clients use short-lived contributor tokens.** A partner app whose mobile or web client calls OTWD directly gets a contributor token for the signed-in contributor from its own server, which calls `POST /v1/contributor-tokens` with its key. The token is opaque, bound to the partner app and one pseudonymous ID, lives 15 minutes by default and an hour at most, and only covers that contributor's submissions, photo uploads, appeals, replies and their status. A submission sent with it must name the same pseudonymous ID, or it is refused. The client never holds the key, and a stolen token is worth one contributor for an hour at most. Partner apps that prefer it can keep sending submissions from their own server with the key, as before.

**Attestation is the partner's check, recorded by OTWD.** Before minting a token, the partner's server can check that the request comes from a genuine install of its app: Apple App Attest on Apple platforms and the Play Integrity API on Android. Both are designed to be verified on the developer's own server. Apple's App Attest docs say to send the attestation object "to your server for verification", with "a unique, one-time challenge from your server" of "at least 16 bytes", after which "your server can require the app to assert its legitimacy for any or all future server requests" ([Establishing your app's integrity](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity)). Apple also says "Not all devices can use the App Attest service", that apps should "gracefully bypass the service" on those, and that only action, extensible SSO and watchOS extensions are supported among app extensions. For Play Integrity, Google's docs say the API "works best when used alongside other signals as part of your overall anti-abuse strategy and not as your sole anti-abuse mechanism", and that by default "your app can make up to 10,000 total requests per day across all installs" ([Play Integrity API overview](https://developer.android.com/google/play/integrity/overview)). Standard requests bind a verdict to a request with `requestHash` and classic requests with a `nonce`, and the verdict token is decrypted through Google's servers or, for classic requests, optionally on the developer's own server ([standard requests](https://developer.android.com/google/play/integrity/standard), [classic requests](https://developer.android.com/google/play/integrity/classic)).

OTWD does not verify these itself. App Attest verification needs the app's App ID, and Play Integrity decoding runs in the app's own Google Cloud project, both of which belong to the partner. Instead the token request carries `attestation` (method and when it was verified), and OTWD records it with every submission made with the token and weighs it in the key's trust score. Attestation is optional in the contract, because not every device supports it and both vendors describe it as one signal among several. OTWD's own trust scores, per-contributor rate limits and moderation stay the main defence.

**Rotation without downtime.** A partner app has at most two active keys. It creates a new key in the developer portal, deploys it, watches `last_used_at` on the old key stop changing, and revokes the old key with reason `rotated`. Key management (`GET` and `POST /v1/partner/keys`, `POST /v1/partner/keys/{api_key_id}/revoke`) authenticates with the developer portal's OIDC sign-in, never with an API key, so a leaked key cannot create keys or revoke the real one.

**Rate limits per contributor per key.** Besides the per-key limits ([ADR 0020](0020-envoy-gateway-for-keys-quotas-and-rate-limits.md)), submissions are limited per pseudonymous ID per key, whether they arrive with the key or a contributor token, and the limit for new pseudonymous IDs per key per day is set by the key's trust score. Responses name the policy in the `RateLimit-Policy` and `RateLimit` fields of the IETF RateLimit header fields draft ([draft-ietf-httpapi-ratelimit-headers-11](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/)), and a contributor limit answers 429 with problem type `contributor-rate-limited`. The numbers are set per tier and published in the developer portal, not in the contract.

**Revoked and abused keys.** Revoking a key stops it, and every token minted with it, within the gateway's key cache time of at most 60 seconds. A partner that revokes a key as `compromised` gives `compromised_since`. OTWD can revoke a key as `abused`. Either way, submissions from that key after that moment that are still undecided are rejected with reason code `api_key_compromised`, and the changes they already produced are listed for a moderator, who can revert them in one decision with cause `abused_api_key`. Each revert is a change with origin `revert` naming the change it undoes ([ADR 0036](0036-record-lifecycle-and-change-origins.md)). The key's trust score is reset, and the trust scores of the pseudonymous IDs seen only through it are discarded.

## Considered options

- **OAuth 2.0 Token Exchange (RFC 8693).** It defines a token endpoint with `grant_type` `urn:ietf:params:oauth:grant-type:token-exchange`, a required `subject_token` and `subject_token_type`, an optional `actor_token`, and an `act` claim to express delegation ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.txt)). Not chosen for now: the partner's server would have to issue its own subject tokens in a format OTWD accepts, which is more work for partners than a JSON request with the pseudonymous ID their submissions already carry. The endpoint's shape is close enough to move to RFC 8693 later as an additional, standard way in.
- **Keep keys in clients and rely on rate limits.** Rejected: a key pulled from an app can mint unlimited pseudonymous IDs, so per-contributor limits would not hold.
- **OTWD verifies App Attest and Play Integrity itself.** Rejected: it needs each partner's app credentials and Google Cloud project, and it would put platform vendors' verdicts on OTWD's critical path.
- **Require attestation for every token.** Rejected: Apple says not all devices support App Attest, web clients have neither, and both vendors present it as one signal.
- **Manage keys with an API key.** Rejected: a leaked key could then lock out its owner.

## Open questions

- Whether contributor tokens should be sender-constrained to a key held on the device, so a stolen token cannot be replayed from elsewhere. That needs a standard checked against its primary source before it is adopted.
- The OIDC provider is not chosen yet ([ADR 0022](0022-self-hosted-oidc-for-direct-contributors.md)), so `auth.opentouring.org` in the OpenAPI document is the planned host, not a running service.

## Consequences

The OpenAPI document gains the `ContributorToken` and `PartnerAdmin` security schemes, the token and key management endpoints, and the token as an alternative to the key on submissions, photo uploads, appeals, replies and submission status. The website uses its own key ([ADR 0023](0023-the-website-is-just-another-api-client.md)) only on its server: its signed-in islands call the API through that server or with contributor tokens, so the key never reaches a browser. `CONTEXT.md` defines contributor token. The founding partner app sends its submissions from its server or with contributor tokens before `v1.0.0`.
