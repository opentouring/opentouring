# OTWD JSON Schema, version 1

This directory holds the data contract for OTWD: JSON Schema (draft 2020-12) documents for the four record types (sites, road restrictions, road segments and ferry services), submissions, moderation decisions, verdicts and changes, the governed lists and their translations, their mappings to OpenStreetMap and schema.org, examples, and a validator. The OpenAPI spec in `../api/` references these files directly, and the Rust API, the Python pipelines, the website and the SDKs are all built against them.

Every schema has an `$id` under `https://schema.opentouring.org/otwd/v1/`. References between files are relative, so the files resolve both from disk and from that base URL.

## Public IDs

A site's public ID looks like `otwd:site:01KR6JW0QBNHM90XV3GS9Y2G26`: the namespace `otwd`, the kind of thing, and a ULID. Road restrictions, road segments and ferry services use the same form with their own kind: `otwd:road_restriction:...`, `otwd:road_segment:...` and `otwd:ferry_service:...`. The kind is the record type's name in snake_case, like `partner_app` and `seed_source`, so an ID says what it names without a lookup. Every other OTWD identifier follows the same form (`otwd:submission:...`, `otwd:decision:...`, `otwd:verdict:...`, `otwd:photo:...`, `otwd:contributor:...`, `otwd:partner_app:...`, `otwd:upload:...`). Seed sources are the one exception: they are curated by maintainers, so they use a readable slug such as `otwd:seed_source:au-example-parks-campgrounds`.

The prefix makes an ID self-describing wherever it ends up. Partner apps store OTWD IDs next to IDs from other sources in their own databases, logs and support tickets, and `otwd:site:` says where the ID came from and what it names. The kind segment also stops a submission ID being used where a site ID belongs, because the patterns in `common.schema.json` reject it.

The ULID part is 128 bits, so it fits a Postgres `uuid` column. It can be generated without coordination by any service, including the Rust API, the GitHub App, the Python pipelines and a contributor writing a record file by hand. It sorts by creation time, which keeps database indexes compact, and it uses Crockford base32 in upper case, which avoids characters that are easy to misread (I, L, O, U). It reveals when the ID was created, which is harmless because `created_at` is public anyway. Sequential numbers were ruled out because they need a central counter and invite scraping by counting.

Colons are allowed in a URL path segment (RFC 3986), so the API uses the full ID in paths, for example `/v1/sites/otwd:site:01KR6JW0QBNHM90XV3GS9Y2G26`, without percent-encoding. Website addresses use only the ULID part, as in `/sites/nt/pandanus-flats-caravan-park-01KR6JW0QBNHM90XV3GS9Y2G26`, which converts back to the full ID without loss.

A public ID never changes and is never reused. A closure keeps its ID. A merge leaves the losing record as a stub with `status` merged and `redirect_to` naming the survivor, and the API answers it with a 301. A record recorded as the wrong record type becomes a `replaced` stub whose `redirect_to` names its replacement, of another type, also answered with a 301. A record that should never have been published becomes a `retracted` stub with nothing but its ID and status, answered with a 410. An unmerge brings a merged stub back as a record under the same ID, and a split keeps the record's ID for one part and gives the others new IDs ([ADR 0036](../docs/adr/0036-record-lifecycle-and-change-origins.md)). These rules are the same for every record type: merges, unmerges and splits stay within one record type, and a replacement always leaves it.

Each change in `change.schema.json` has a `kind`, what happened to the record, and an `origin`, why: a `submission` names its submission and decision, a `revert` names the change it undoes in `reverts_seq`, a `takedown` names its reason and never its requester, and a `recompute` updates only `/derived` and has no decision. `confirm_facts` submissions become `facts_confirmed` changes, which add to `confirmations` without changing a value.

## The repository form

Live data is kept in a public data repository per country, one JSON file per record ([ADR 0046](../docs/adr/0046-live-data-in-a-public-git-repository-per-country.md)). A file holds the record in the repository form: the full form without the values the read model computes when it loads the file. Provenance has no `confidence` or `change_seq`, and the record has no `updated_at`, `change_seq` or `derived` values. Everything else, the facts, their provenance and the lifecycle rules, is the full form's.

Each `<record-type>-repository.schema.json` is the full form with two dynamic anchors overridden. `Fact`, `StatusFact` and `Photo` reach provenance through `$dynamicRef: "#provenance"`, which resolves to `Provenance` when a full form is validated and to `RepositoryProvenance` when a repository form is. `FullRecord` checks the computed values through `$dynamicRef: "#computed"`, which requires them in the full form (`ComputedValues`) and forbids them in the repository form (`RepositoryComputedValues`). So each record type keeps one fact table, and anyone can validate a data repository file with any JSON Schema 2020-12 validator. Name a file `*.site-repository.json` (and so on) for `tools/validate.py` to check it as one, or run `tools/validate.py --data-repository DIR` to check every record file in a whole data repository at once, by the record type folder it sits in (see "Validating" below). Checks that need derived values, such as a schedule's time zone being one of the record's, are skipped for the repository form because the loader computes those values.

## Facts and provenance

Every fact carries its provenance: what kind of source supplied it, through which partner app or seed source, when it was observed, when OTWD recorded it, with what confidence, and the change that set it. In the full form each fact is an object holding the value and its provenance side by side:

```json
"rig_limits": {
  "value": { "max_length_m": 7, "big_rig_suitable": "no" },
  "provenance": {
    "source_kind": "partner_app",
    "partner_app_id": "otwd:partner_app:01KJK8W2CAWJC5J54FT58K4JGM",
    "observed_on": "2026-09-06",
    "recorded_at": "2026-09-08T23:10:00Z",
    "confidence": 0.8,
    "change_seq": 20211
  }
}
```

Published provenance never identifies a contributor ([ADR 0038](../docs/adr/0038-contributor-identity-in-published-data.md)). It names the partner app, or the seed source, and the date. A direct contributor appears as `source_kind` contributor, with their `display_name` only if they chose to be named. Contributor IDs, pseudonymous IDs and submission IDs stay in the submission log, where moderation, trust scores and abuse handling use them, and `tools/validate.py` fails any record or change that carries one, in any field. Confirmations publish a count of different contributors, never who they were.

Every record type uses the same fact wrapper, `Fact` in `common.schema.json`, and constrains its `value` with the value shape from `values.schema.json`. The parts every record shares live in `common.schema.json` once: the full form envelope (`FullRecord`: identity, `StatusFact`, timestamps, `change_seq`, photos and the merge rule), the compact form envelope (`CompactRecord`: the same with the closure fields flattened, the primary `name`, `attribution`, `min_confidence` and `safety_facts_observed_on`), and derived values (`PointDerivedValues` and `LineDerivedValues`, wrapped as `PointDerived` and `LineDerived` in the full form). A change to how provenance, status or photos work is made once for all four record types.

Each record type's full form schema defines its fact table once, in three definitions the other schemas reuse:

- `Facts`: every fact wrapped with its provenance, for the full form.
- `FactValues`: every fact as a plain value. The compact form and the submission schema reference it directly.
- `RequiredFacts`: the facts a record of that type always has, used by the full form, the compact form and the submission that creates one.

### What JSON Schema cannot share

JSON Schema has no templates, so two things are written twice and checked by `tools/validate.py` instead. `Facts` and `FactValues` both list every fact name, because one wraps each value in `Fact` and the other does not: the validator checks that they name the same facts with the same value shapes. The `update_facts` rule that the required facts cannot be removed lists them as JSON Pointers (`/facts/location`), which JSON Schema cannot build from names: the validator checks those lists against `RequiredFacts`. Schemas that combine definitions close the object with `unevaluatedProperties: false`, because `additionalProperties` cannot see properties defined in a referenced schema.

For a site, facts live under `facts` (names, location, site types, description, opening and reception hours, prices, rig limits, access, pets, accessibility, bait notices, bookings, contact, capacity, stay limits, camping rules, permits, quiet hours, age rules, firewood, seasonal operation, tidal access, water notices and location sensitivity). Facilities live under `facilities`, one fact per facility code, so each facility has its own provenance. Photos, which any record type can have, carry provenance too. The values derived from the location (country, subdivision, locality, time zone) sit under `derived` without provenance, because OTWD computes them and nobody submits them.

The grain is one provenance per fact, not per value inside it. A price list or a set of opening hours is reported, checked and replaced as a whole by one contributor or one seed source, so splitting provenance further would add size without telling a reader anything new. Facilities are separate facts because different people report them at different times.

The compact form (`site-compact.schema.json`) is the same site with each fact replaced by its value. It keeps three things from the provenance so readers of the compact form are not left blind: an `attribution` list of structured entries with every credit the facts require (text, licence, links and the changes notice CC BY asks for, [ADR 0037](../docs/adr/0037-structured-attribution-and-photo-licences.md)), `min_confidence` (the lowest confidence on the site) and `safety_facts_observed_on` (the oldest observation among its safety facts). It also fills in the facilities that are read from other facts, so filters work the same way on every facility code.

### Trade-off

Keeping value and provenance together in the full form means a fact can never be separated from its source, a seed source update can replace one fact without touching a contributor's newer fact beside it, and a moderator or partner app can weigh each fact on its own. The cost is size and verbosity: a full site is several times larger than the compact one, and reading a value takes one extra step (`facts.prices.value`). Two alternatives were weighed. A parallel provenance map keyed by field path keeps values small but lets the two drift apart, and every consumer has to join them. Provenance only on the site, or only in the change history, is compact but cannot express a site whose facts come from different sources, which is the normal case once seed data and contributions mix.

The compact form removes the verbosity for the common case. Map apps, lists and bulk analysis read compact sites. Apps that show sources, weigh freshness or contribute corrections read the full form for the sites they need.

## Record types and geometry

Sites and road restrictions are points: their `location` fact is a latitude and longitude. Road segments and ferry services are lines: their `geometry` fact is a GeoJSON LineString or MultiLineString (RFC 7946) in WGS84, longitude first. GeoJSON responses and bulk downloads turn locations into Point geometry. There are no map tiles.

A **road restriction** has a `structure` (from `structures.json`) with a `passage`: over (the road crosses it, so weight and width matter), under (the road passes beneath it, so vertical clearance matters), through (a tunnel, gate or ford) or along (a limit signed on the open road). Each structure code lists the passages it allows. Its limits are `vertical_clearance`, `width_limit`, `weight_limit` and `length_limit`, and it always has at least one, or a `flood_depth_marker` at a ford or causeway, which only those two structures can have. Vertical clearance and width hold every known figure in `measurements`, each with a basis (signed, surveyed, measured or unknown), optional heading of travel or lane, date and survey certificate, plus `lowest_m`, the lowest figure of any basis, and `lowest_basis`, the basis of that figure. Rig filters and apps compare a vehicle with `lowest_m`, because a measured or surveyed figure below the sign is the one that strikes the vehicle. Every height and width, including each figure, is at most 10 m, so a figure in feet such as 13.5 fails instead of passing as metres.

A **road segment** has a `surface` (from `surfaces.json`, with a condition), a `vehicle_access_class` (from `vehicle-access-classes.json`, ranked from 2WD to closed to vehicles), `towing_permitted`, a `seasonal_closure`, optional weight and length limits that apply along its whole length, a `pet_transit` rule, any `bait_notices`, `camping_rules`, `permits` and `tidal_access`. `towing_permitted` comes from contributors, so its provenance is never a seed source and a seeding pipeline submission cannot propose it.

A **ferry service** joins exactly two `terminals`, which are sites whose site types include `ferry_terminal`, a fixed check. A service that calls at more places is recorded as one ferry service per crossing. It lists its `accepted_vehicle_classes` (from `vehicle-classes.json`), its `vehicle_limits` (overall and per vehicle class, plus the total load per crossing), `fares` per vehicle class and vehicle band, `bookings`, `operating_hours`, `crossing` details, `accessibility`, a `pet_policy` and any `seasonal_closure`. Vehicle bands and length limits are combined lengths, including the drawbar and anything towed, as operators price them. A fare's `crossings` is 1 for a one-way fare and 2 for a return. Fares and vehicle limits may only name vehicle classes the service carries.

A **seasonal closure** is a recurring window (month and day, with `dates_year` saying which year's published dates they came from) plus the authority and a link to its current information. A one-off closure of any record, such as a bridge shut by flood damage, is the record's status `temporarily_closed`, with `closed_on`, `reopens_on`, `closure_authority` and `closure_info_url`, named the same in the full form, the compact form and a `report_closure` submission. Short incident closures stay with the authority.

## Time

Every instant, such as `recorded_at`, `retrieved_at`, `decided_at`, `created_at` or `applied_at`, is a `Timestamp`: RFC 3339 in UTC with the `Z` suffix. Any other offset fails. Local schedules (opening and reception hours, check-in times, generator hours, ferry operating hours, seasonal closures and the periods of access and fire policy) are local clock times (`LocalTime`), local dates (`LocalDate`) and days of the year (`MonthDay`), read in the record's IANA time zone and never converted to UTC, so a 6:00 am departure stays at 6:00 am through daylight saving changes ([ADR 0032](../docs/adr/0032-utc-for-instants-local-time-for-schedules.md)).

A point record has one derived `time_zone`. A line record has `time_zone`, its default (the zone at its start), and `time_zones`, every zone it passes through in order. A schedule on a line that belongs to another of those zones names it in its own `time_zone`, which `OpeningHours`, `SeasonalClosure` and a ferry service's `Fares` accept, and `tools/validate.py` rejects a schedule zone that is not one of the record's zones. A line that returns to a zone lists it again, so a track from South Australia into Victoria and back has `time_zones` Adelaide, Melbourne, Adelaide, but no zone appears twice in a row.

## Unknown, absent and safety facts

A fact or facility missing from a site is unknown. A facility recorded with `available: false` is known to be absent. The difference matters most for drinking water and rig limits, so apps must never present an unknown as a no, or as unlimited.

Safety facts are the facts a traveller relies on for safety: drinking water and non-potable water, road access, rig limits, the site's fire policy (`fires_allowed`) and its fire district, bait notices (`bait_notices`) on a site or road segment, water notices (`water_notices`) on a site, tidal access (`tidal_access`) on a site or road segment, the drinking water point and emergency hospital site types, a road restriction's location, every limit on it and its flood depth marker, a road segment's geometry, vehicle access class, towing permitted, seasonal closure and limits, and a ferry service's geometry, terminals, accepted vehicle classes, vehicle limits and seasonal closure. A site's location is not a safety fact. An absent limit on a road restriction, road segment or ferry service is unknown, never unlimited. They are marked with `"x-otwd-safety-fact": true` in the full form schemas and `safety_fact: true` in the site type and facility lists.

Routing always sends a change to a safety fact to a moderator, and the always-human list is derived, never declared. A moderation decision's `routing` records the submission's kind, record type and the fields it touched. The fixed checks, and `tools/validate.py` for the examples, put a submission on the list when its kind creates a record, closes one or merges records, or when any field it touches carries the safety fact marker for its record type or the `x-otwd-always-human` marker, which `location_sensitivity` carries because it is not a safety fact but every change to it needs a person ([ADR 0045](../docs/adr/0045-sensitive-locations-are-published-generalised.md)). A decision by a routing rule on such a submission fails, whatever `always_human` says, and a change that touches a marked field must not say `safety_fact_changed: false`.

Accessibility is not a safety fact, so routing does not send every change to it to a moderator. A wrong yes can strand a traveller who relied on it, while a wrong no or limited costs far less, so the fixed checks flag a submission that raises wheelchair access for any feature to yes, sets `step_free_access` or `changing_places` to true, or sets `toilets.key_required` to false. The flag is recorded as `accessibility_raised` in the moderation decision's `routing.fixed_check_flags`, the submission goes to a person, and a decision by a routing rule on it fails validation. It sits beside the always-human list rather than on it, because it depends on the values submitted, not only on the fields touched ([ADR 0033](../docs/adr/0033-structured-accessibility-on-sites-and-ferry-services.md)). The `sensitive_location` flag works the same way: the fixed checks set it on a submission that changes the location, names or description of a site whose location is sensitive, or adds a photo of one, and a routing rule cannot decide it.

Fire bans declared by fire authorities change daily and are never recorded in OTWD. `fires_allowed` is only the site's standing policy, and `fire_district` names the fire authority and district the site falls in, with `ban_info_url` pointing to the authority's official live fire ban information. OTWD computes `fire_district` from the location against a seed source's district boundaries, so contributors never submit it. Apps that show `fires_allowed` should link to `ban_info_url` beside it.

## Governed lists

`site-types.json` and `facilities.json` hold every site type and facility code with a label and a description in en-AU, the attributes it carries, whether it is a safety fact, and its OSM and schema.org mappings. `structures.json` (with the passages each allows), `surfaces.json`, `vehicle-access-classes.json` (with a rank), `vehicle-classes.json`, `key-schemes.json` (with the countries each scheme is used in), `pet-species.json`, `self-contained-schemes.json` (with the countries each is used in and whether it is statutory) and `location-sensitivity-reasons.json` (with the finest grid each allows) follow the same format, described in `vocabulary.schema.json`. Codes are stable: a code is never renamed or reused, and one that is no longer wanted is marked `deprecated` and keeps its meaning.

The schemas accept any code that matches the code pattern, not only the codes in the lists. That way a site that uses a facility added in a later minor version still validates against an older copy of the schema. Membership of the governed lists is checked by the API and by `tools/validate.py`, and consumers ignore codes they do not recognise. Facilities with attributes are checked strictly: each has its own schema in `values.schema.json`, and the validator confirms the attributes in `facilities.json` match it.

### Translations

en-AU is the reference language. Every other language is a translation in `i18n/<language>/`, one file per governed list (for example `i18n/de/facilities.json`), following `translation.schema.json`. A translation holds only labels, descriptions and attribute descriptions, keyed by code. Codes, safety facts, attributes and mappings stay in the reference list, so a translation cannot change what a code means, and `tools/validate.py` rejects a translation that names a code or attribute the reference list does not have, carries any other field, or sits in a folder that does not match its `language`. The API serves the governed lists in the language asked for in `Accept-Language`, and missing text falls back to en-AU as [ADR 0031](../docs/adr/0031-governed-lists-and-the-api-are-translatable.md) sets out. `i18n/README.md` explains how to add a translation.

Free text in records, such as names, descriptions and notes, is never translated by OTWD. It is `LocalisedText` or `Notes`, which keep the language the contributor wrote in beside the text.

Four facility codes are read from other facts rather than stored: `pets_allowed` and `dog_off_leash` from `pets`, `big_rig_access` from `rig_limits.big_rig_suitable`, and `accessible_facilities` from `accessibility`. Storing them twice would let the two copies disagree, so the full form and submissions reject them in the facilities map, and the compact form and the API filters fill them in. The `stored_as` entry in `facilities.json` is the one list of these codes, with the rule for each. JSON Schema needs the codes spelled out to reject them, so `StoredFacilities` and the site's `FacilityFacts` list them too, and the validator fails when either list differs from `stored_as`.

The fuel site type records that a fuel station is there and its non-fuel facts. Fuel prices, grades and brands are outside OTWD.

## Versioning

Until version 1.0.0 is released, the schema and the API are a draft. Release means a `v1.0.0` tag on this repository, made before any partner app outside the project integrates ([ADR 0030](../docs/adr/0030-schema-and-api-stay-a-draft-until-v1-0-0-is-released.md)). Before that tag, any field, code or endpoint can change or be removed without a new major version, and documents carry `schema_version` `1.0`. From the tag on, the rules below apply.

Documents carry `schema_version` (for example `1.0`). Minor versions only add optional fields, governed list entries, values of open enumerations and record types in the registry, so a document valid under 1.0 stays valid under every 1.x, and a consumer written for 1.0 can read any 1.x document by ignoring what it does not know.

### Open enumerations and record types

Every list of values in the schema is a governed list, an open enumeration or a closed enumeration ([ADR 0035](../docs/adr/0035-open-enumerations-and-a-record-type-registry.md)). An open enumeration, such as change kinds, submission kinds, moderation outcomes or price units, is a string matching `EnumCode`, with the values known at this version in `x-otwd-known-values` and, in its description, what a consumer does with a value it does not know. OTWD sends only known values, and `tools/validate.py` holds every example to them. A consumer's validator ignores the `x-otwd-` keywords, so it accepts values added in later minor versions. A closed enumeration, such as record status or towing permitted, is a plain `enum` that changes only in a new major version.

Record types are listed in `record-types.json` and served at `/v1/record-types`. `RecordId` and `RecordType` accept any snake_case record type code, apart from the kinds reserved for other OTWD identifiers, and `x-otwd-registry` holds producers to the registered ones. A consumer skips records, changes and bulk downloads of a record type it does not know. Removing or changing the meaning of a field or code needs version 2, published under a new `$id` base (`.../otwd/v2/`) and served under `/v2` of the API alongside `/v1`.

## Validating

```sh
python3 -m pip install -r schema/tools/requirements.txt
python3 schema/tools/validate.py
```

`tools/check-schema.sh` does the same in `.tools/venv` and also checks the script's formatting with `ruff format --check`. With no arguments the script checks every schema against the 2020-12 metaschema, checks the governed lists against `vocabulary.schema.json` and against the per-facility schemas, checks that each record type's `Facts`, `FactValues`, compact form and submissions name the same facts with the same value shapes and use one `RequiredFacts`, validates every example with format checking on, and applies the rules the API enforces beyond JSON Schema: governed list codes, ISO 3166-2 subdivisions inside the record's countries, IANA time zones, a structure's allowed passages, the `lowest_m` rule, fares and limits only for carried vehicle classes, the always-human list derived from the safety fact markers, pet species codes and species listed once, no species allowed where pets are not, bait notices and water notices that end after they start, key schemes and self-contained schemes used in the record's country, self-contained vehicles required only where camping is restricted, a site's season given once, flood depth markers only at fords and causeways, a sensitive site's coordinates on a grid at least as coarse as its reason allows, a GeoJSON feature's geometry equal to its site's published location, no accessible toilets counted where wheelchair access to toilets is no, `ambulant` agreeing with `ambulant_count`, the compact form's `accessible_facilities` matching the accessibility fact, the codes excluded from stored facilities matching `stored_as`, ferry terminals that are `ferry_terminal` sites (in the examples, every terminal must be a site among the valid examples), record types across merges, unmerges, splits and replacements, photo licences against their provenance, and a few other cross-field rules. It walks every published document (records and changes) and fails any contributor, submission, upload or API key identifier in it. One table of fact checks serves every record type and submissions, and the record types come from `record-types.json`, from which the schema file names and document suffixes follow. Open enumerations and record types are checked as for a producer, and every file in `examples/consumer` must pass the plain validator a consumer uses while failing the strict one on a value this version does not know. It also checks every translation in `i18n/` against `translation.schema.json`, its reference list and its folder. Every file in `examples/valid` must pass, including the translations under `examples/valid/i18n`. Every file in `examples/invalid` must fail with the error fragment named for it (by its path below `examples/invalid`) in `examples/invalid/expected.json`, so an invalid example cannot pass the test by failing for an unrelated reason. An invalid example can name a valid example in `$base` and list JSON Patch operations (add, replace or remove) in `$patch`, so it states only what makes it invalid. The validator builds the document from the two before checking it. The exit status is 0 only when all of that holds.

To check documents of your own, name them. The schema is chosen from the file name suffix (`.site.json`, `.site-compact.json`, `.site-feature.json`, `.road-restriction.json`, `.road-restriction-compact.json`, `.road-segment.json`, `.road-segment-compact.json`, `.ferry-service.json`, `.ferry-service-compact.json`, `.submission.json`, `.verdict.json`, `.moderation-decision.json`, `.change.json`):

```sh
python3 schema/tools/validate.py my-export/*.site.json
```

A file at `i18n/<language>/<list file>`, anywhere, is checked as a translation, including the check that its folder matches its `language`.

To check a whole data repository, name its root:

```sh
python3 schema/tools/validate.py --data-repository my-clone-of-otwd-au
```

This walks `<state>/<record-type>/*.json`, taking each file's schema from its record type folder, checking its file name is the record's own ULID, and checking the state and record type folders are known ones. It does not check that a record's state folder matches its location, which is the loader's job. It requires `otwd.json` at the root and checks its content against `otwd-config.schema.json`, including the schema tag. Every other file or folder at the root fails, except `README.md`, `LICENSE`, `ATTRIBUTION.md`, `otwd.json`, `CODEOWNERS`, `AGENTS.md`, `.gitignore`, `.gitattributes` and `.github/`. A checkout's own root `.git` is skipped, and a `.gitkeep` is allowed directly inside a state folder so an empty one can exist in git. It fails a symlink anywhere in the repository except inside `.github/`, so a pull request cannot make the check read outside the checkout. It reads each record and `otwd.json` as plain JSON, once: a file must be a regular file of at most 1 MiB, strict UTF-8, and must not use `$base` or `$patch`, and a record must not carry a top-level `$comment`, which the repository schemas do not allow. `otwd.json` may keep its `$comment`. One public id anywhere else in the repository, under any record type or state folder, fails on both paths, because a record is one file. A file over the limit is told to split the record, such as a long road segment. A file that is too large, too deeply nested or not valid JSON is a problem on that file, not a crash. It exits 1 with a usage message when the folder does not exist. Record type folder names are the last segment of each record type's `collection` in `record-types.json`. Files under `.github/`, such as `labels.yml`, are not checked.

## Examples

The valid examples are invented Australian sites with plausible names and coordinates: a free camp in Queensland, a caravan park in the Northern Territory, a national park campsite in New South Wales imported from a seed source, a council dump point in Victoria, a rest area in Western Australia, a showground in South Australia that is temporarily closed, a lookout in Tasmania with a photo, and a merged site. Two of them also appear in the compact form. Victorian examples cover the other record types: a low rail bridge with signed and measured clearances per direction and lane, a timber bridge with a weight limit, a 4WD-only track with a seasonal closure, a sealed road divided at a town entry, a merged duplicate track, ferry terminal sites, and a vehicle ferry that carries cars towing caravans with length bands and fares, with compact forms of three of them. A 4WD track that loops from South Australia into Victoria and back shows a line with several time zones and a closure read on the Victorian clock. A New Zealand freedom camping area requires certified self-contained vehicles, a Queensland beach campground is reached along the beach at low tide with camping and vehicle permits, a Tasmanian holiday park is adults only with quiet hours, a season and a boil water notice, a Northern Territory transit road needs a land council permit, a Queensland causeway has a flood depth marker, and a Northern Territory walk whose location is sensitive is shown in the full, compact and GeoJSON feature forms with its generalised location, with the submission, decision and change that marked it. The rest cover every submission kind (including a photo of a road restriction), a verdict, six moderation decisions (one sent to a person by the accessibility_raised check) and five changes. Phone numbers use the ranges ACMA reserves for fiction, and web addresses use the `example.com` and `example.org` domains.

## Accessibility

A site's or ferry service's `accessibility` fact gives wheelchair access per feature as yes, limited or no, each with an optional note. A site's features are `arrival` (entrance, reception or the arrival point), `toilets`, `showers`, `parking`, `paths`, `pitches` (the individual camping spots), `cabins` and `camp_kitchen`, from `SiteAccessFeature`. A ferry service's are `boarding`, `seating` and `toilets`, and access at its terminals is recorded on the terminal sites. `toilets` holds the accessible and ambulant counts, recorded only when someone counted, `ambulant` for whether an ambulant toilet exists, `changing_places`, `key_required` and a `key_scheme` from `key-schemes.json`, which must be a scheme used in the record's country. `basis` is required and says whether the fact was assessed to a named standard (given in `standard`), signposted, reported by the operator or a seed source, or observed by a contributor. A feature that is absent is unknown.

`accessible_facilities` is read from the fact, and is absent when no feature is recorded. It is not available, with no attributes, when arrival is no or every recorded feature is no: a traveller who cannot get in cannot use the rest. Otherwise it is available, with `wheelchair` yes when arrival is yes and every recorded feature is yes, and limited in every other case, including an arrival that is not recorded, which gives limited at best. `features` lists the features whose access is yes. OSM `wheelchair=yes`, `wheelchair=limited` and `wheelchair=no` map to the three outcomes. `paths.path_surface` uses its own values, chosen for wheelchairs, and is not the surface governed list.

## Pets and bait notices

A site's `pets` fact has a general `allowed` rule (yes, on_leash, by_arrangement or no), a rule per species in `species` from `pet-species.json`, and `conditions`: `max_pets`, `size_or_breed_restrictions`, a `fee` per pet, the `areas` pets may stay in (`whole_site`, `designated_pitches`, `all_pitches`, `cabins` or `day_use_area`) and `not_allowed_periods` each year, as local month and day. `allowed` must not be no when a species rule allows that species. A ferry service's `pet_policy` says whether pets are `carried` and lists the `arrangements` (in_vehicle, kennel, pet_friendly_cabin, on_deck_on_leash, in_carrier), each with its species, `booking_required` and fee. A road segment's `pet_transit` is yes, in_vehicle_only or no, with the authority and its `info_url`. Assistance animals are covered by law and are outside all of these facts.

`bait_notices` on a site or road segment lists poison bait notices, each with the area, the poison, the authority, its `info_url` and local `from` and `to` dates. It is a safety fact, so every change goes to a moderator. OTWD records the notice as signed or published and never the authority's live baiting programme, following the fire policy approach ([ADR 0034](../docs/adr/0034-pet-policies-pet-transit-and-bait-notices.md), [ADR 0026](../docs/adr/0026-fire-policy-not-fire-bans.md)). Records keep a notice after its `to` date until a moderator removes it, so a consumer that reads `bait_notices` checks the dates. The API's `has_bait_notice` filter matches only notices current on the request date: `from` on or before it, and `to` on or after it or absent, as local dates in the record's time zone, or in the notice's own `time_zone` when it has one (a road segment can cross zones). A missing notice is unknown, never proof that no baits are laid.

### Seed mappings for pets

| Seed source field             | OTWD                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------- |
| NSW Rest Areas `pets_allowed` | `pets.allowed` yes when true, no when false. The dataset gives no species or conditions |

No open dataset found carries ferry pet policies, pet transit rules or bait notices. They come from contributors, who report the operator's or authority's published rules and signs.

## Camping rules, permits and site rules

`camping_rules` on a site or road segment says whether overnight camping is `allowed`, `restricted` or `prohibited`, with the council's or land manager's `authority` and `info_url`, and `self_contained` says whether only certified self-contained vehicles may camp and which schemes from `self-contained-schemes.json` the authority accepts. A scheme must be used in the record's country, and `required` true makes camping restricted. `permits` lists the permits a traveller needs (`park_entry`, `camping`, `land_entry`, `transit` or `other` with notes), each with its issuing authority, `info_url`, `in_advance` and `free`. `tidal_access` on a site or road segment is a safety fact: access depends on the tide, with `low_tide_window_h`, the tide `station` and the tide authority's prediction page, never tide times. A site also has `quiet_hours` (local times), `age_rules` (`children_allowed`, `min_guest_age` for an adults-only site, `min_booking_age`), `firewood` (`for_sale`, `provided`, `collection`) and `seasonal_operation` (the months it operates, as local month and day), which it gives instead of `opening_hours.seasonal_closures`, never both ([ADR 0043](../docs/adr/0043-site-rules-permits-and-amenities.md)).

## Water notices and flood depth markers

`water_notices` on a site lists boil water (`boil_water`), `do_not_drink`, `do_not_use` and `other` notices for its supply, each with the area, local `from` and `to` dates and the issuing authority's `info_url`. `flood_depth_marker` on a road restriction at a ford or causeway says whether a depth marker is `present`, with the road authority's page for current conditions. Both are safety facts, and OTWD records neither live water quality nor live depths ([ADR 0044](../docs/adr/0044-water-notices-and-flood-depth-markers.md)).

## Sensitive locations

A site with a `location_sensitivity` fact, whose `reason` comes from `location-sensitivity-reasons.json`, is published with a generalised location: `lat` and `lng` rounded to the nearest multiple of `location.generalised.cell_deg` (0.01, 0.1 or 1 degree, no finer than the reason's `min_cell_deg`), no `accuracy_m` and no derived `locality`. The full form, the compact form and the GeoJSON feature (`site-feature.schema.json`, whose geometry must equal the published location) all enforce it, and `tools/validate.py` checks the grid. Submissions carry the exact position and never `generalised`, and OTWD holds the exact position privately for moderation. Every change to `location_sensitivity` is on the always-human list, and later changes to the site's location, names, description or photos carry the `sensitive_location` fixed-check flag ([ADR 0045](../docs/adr/0045-sensitive-locations-are-published-generalised.md)).
